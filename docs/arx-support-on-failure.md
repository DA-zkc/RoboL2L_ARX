# ARX 到位精度与异常后的支撑（2026-11-24）

实验 `dc4b68e01d8c43d3bab5af2de22689a4/v04` 在持物横向转移后，由适配器报
`arx_pair_endpoint_not_verified: left`。左 J5 回执差约 0.02485065 rad（1.424°），
超过部署适配器的 1° 到位门槛。下降放置尚未派发。此处不是 SDK 硬件故障报告。
旧异常分支对双臂调用 `protect_mode()`，使关节 Kp 和前馈力矩归零，仅保留速度阻尼，
夹爪仍保持闭合目标。这种模式不能解释为悬空锁定。

## 修复后的行为

- 双臂动作首先等待计划时长和低速反馈；SDK 故障、掉线、非 JOINT 模式等仍停止派发。
- `move_to_pose`、`move_to_joints`、`move_synchronized` 使用调用方的目标公差，
  在最后路点的夹爪动作之前验收，不再额外以 1° 关节误差覆盖调用方的末端精度要求。
- 直接 `execute_trajectory` 的路点仍采用原 1° 关节精度要求。精度不足返回
  `goal_tolerance_not_met`，保留原 JOINT 目标、增益和夹爪目标，不锁成控制器故障，
  不继续该轨迹后续路点或释放夹爪。调用方应依据实测偏差决定后续操作。
  因此旧 v04 程序仍可能因检查 `receipt.ok` 而结束本轮，但不应再因此切入阻尼模式。
- 双臂部分派发、未知回执或运动一直未停稳等仍锁住 Runtime。对于仍健康且在 JOINT
  模式下的活动臂，通过现有 SDK 的 `set_joint_positions(..., duration=0)` 将目标替换成
  新读取的实测位置。零时长由 SDK 根据原有运动限制规划，**不是立即刹停**。
  未运动的健康侧保留目标；夹爪失败也不再让双臂进入阻尼。
- 单臂共享反馈等待函数的异常／超时分支同样不再主动调用 `protect_mode()`。
  原单臂到位精度和错误分类保持不变。
- 已有 SDK 故障、掉线、越限或非位置控制模式时，不清故障、不重新使能、不覆盖原生保护。
  保持请求被拒绝或反馈无效时明确报告不可用。回执始终 `hold_verified=false`：
  接受请求不等于已验证物理保持，主动伺服保持也不等于机械抱闸。

## 离线证据与验证

`tests/test_arx_support.py` 使用模拟 SDK，覆盖历史 J5 超差、末端公差、严公差失败、
失败后不推进路点／不松爪、运动超时、SDK 故障、未知回执以及保持不可用。
原夹爪与双臂回归继续覆盖部分派发和持物闭合。

`.franka-player/diagnostics/20261124-arm-collapse/sdk_hold_probe.py` 仅在软件替身上调用
已安装 SDK 的编译方法和纯轨迹计算器，不构造硬件控制器或连接 CAN。
它验证目标替换后仍为 JOINT，输出原 Kp `[150,150,150,50,10,10]`，保留夹爪目标，
并保留前馈通路（动力学数值为替身值，不证明实际重力补偿精度）。
结果在同目录 `sdk_hold_probe_result.json`。原阻尼模式探针与故障记录也保存在此目录。

代码修复尚未重载在线 Runtime，未进行真机保持／停止距离验收，也未调整控制增益、
负载模型、夹爪标定、关节边界或速度限制。J5 稳态误差的物理来源仍待独立排查。
