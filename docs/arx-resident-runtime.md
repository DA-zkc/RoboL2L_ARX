## 原因与修复范围

旧启动器先退出整个 Runtime 再启动新进程。退出时 `ARXDriver.close()` 调用 `damp()`，进入仅有阻尼的 PROTECT，然后销毁 SDK。之前对精度失败分支的修复没有覆盖这条路径。

现在把双臂 Runtime 的硬件控制部分放在常驻 `robol2l_deploy.arx_owner` 进程中。它是两台 SDK 控制器的唯一持有者，继续使用现有 ARXDriver、模型和站点硬件锁。控制台保留实验、规划、相机和反馈检查，通过固定方法白名单的本机 Unix socket 调用硬件部分；不接受任意代码、导入路径或任意 SDK 方法。相机不是本次常驻拆分的对象，控制台重启会重新打开相机。

## 行为

| 操作／事件 | 处理 |
| --- | --- |
| 普通控制台重载、结束会话 | 撤销动作权限、释放客户端租约；保留双臂 SDK 和控制循环。健康 JOINT 控制器可请求以实测位置替换剩余目标，夹爪原目标不变。不会调用 damp 或关闭 SDK。 |
| 新控制台连接 | 复用原控制器；默认没有运动权限，不恢复旧程序、轨迹或回位。一次只允许一个控制台租约。 |
| 控制台崩溃／失联 | 0.5 秒心跳、3 秒租约到期后禁止旧客户端派发，并对健康 JOINT 控制器请求停止／保持。不强行解除 SDK 故障、掉线或非 JOINT 原生模式。 |
| 指令回复丢失 | 返回结果未知，不重试，不自动重新连接后重放。需新会话处理。 |
| 模型／设备绑定改变 | 拒绝把新配置接到旧模型的控制器上，要求支撑确认后的维护重启。不会偷偷替换正在工作的 SDK。 |
| 旧版服务退出、停止硬件、切换控制库 | 新启动器要求现场确认双臂已可靠支撑。空闲、运动权限关闭、实验结束均不代表支撑已确认。 |
| SDK 关闭结果未知 | 保留句柄和硬件锁，禁止新租约／新控制器；不把关闭异常当作关闭成功。 |

`ARXDriver.close()` 不再自动调用 damp；直接持有 SDK 的内部路径必须显式传入 `hardware_supported=True` 才允许关闭已打开的句柄。另一臂初始化失败时，也不会自动关闭已经健康连接的一臂。

健康 JOINT 下的保持请求沿用 SDK 原生速度、加速度、jerk 限制；这不是机械抱闸，`hold_verified=false`。租约监测不是硬实时急停。底层控制进程崩溃、SIGKILL、断电、CAN／电机故障仍不能由这层软件保证支撑；不能把“进程常驻”称为失电锁定。原生非 JOINT／故障模式不会被软件强行使能。

## 维护与一次性迁移

1. 让当前实验完成或由实验者主动结束。本次开发没有调用暂停、停止、重载或任何运动接口。
2. 现场让双臂得到可靠支撑，不依赖电机悬空保持。
3. 加载新版 8770 启动器。启动器本身不拥有 SDK，但不要操作旧 8771 的断开按钮来绕过新保护。
4. 在启动器的“硬件维护”勾选已支撑确认，执行“维护重启并加载硬件模型”。新版启动器对旧版会话也会先检查实验空闲并记录这次明确确认，再允许它退出。
5. 新 8771 启动时创建或复用常驻硬件进程；在线 `hardware_lifecycle.mode` 应为 `resident_arx_owner_v1`。之后普通“重载控制台”保留 owner instance 和 SDK；修改硬件模型或硬件进程自身代码仍需维护重启。

维护 API 为 `/api/launcher/maintenance/reload`、`/api/launcher/maintenance/stop`，必须携带 `{"hardware_supported": true}` 和现有控制台请求头。此字段代表操作者现场确认，软件不会从编码器姿态推断“已支撑”。运行中的实验仍禁止维护。普通 `/api/launcher/reload` 不带此授权。

如果因模型变化无法附着旧 owner，确认支撑后仍可停止未被任何控制台占用的 owner，再加载新模型。若 owner 不响应而生命周期锁仍被占用，拒绝创建第二个控制器，不自动杀进程。结束控制台后，常驻硬件控制仍可能在运行；需要停硬件时应使用维护入口。
